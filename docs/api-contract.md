# API 계약

프론트가 Figma 화면 기준으로 질문과 결과 데이터 초안을 보냈고, 백엔드가 2026-09-14 에 답했다 (ssokssok-backend `feature/ocr` 기준). 아래 "정해진 것" 이 그 답이다.

- 필드 모양의 최종 기준은 백엔드 Swagger 다. 2026-09-17 부터 프로덕션에서는 닫혀 있어(404) 백엔드 레포에서 본다. `src/types/document-result.ts` 는 Swagger 의 `DocumentResult` 와 1:1 로 맞춰 두었다 (2026-09-15). 지금은 손으로 맞추고, Swagger 에서 타입을 만드는 방식은 미정이다 (`docs/architecture.md` "백엔드 연동")
- 백엔드에 연결하기 전에는 `src/api/` 의 호출 함수가 목데이터를 돌려준다. 연결할 때 함수 안만 바꾼다

## 정해진 것

### 1. 변환 요청: 작업 ID + 폴링

표가 있는 긴 문서는 1~2분 걸릴 수 있어, 요청 하나로 끝까지 기다리지 않는다. SSE 대신 폴링을 쓴다 (모바일 백그라운드 전환에 안정적).

| 메서드 | 경로                          | 설명                                |
| ------ | ----------------------------- | ----------------------------------- |
| POST   | `/documents/convert`          | 변환 시작. `job_id` 즉시 반환 (202) |
| GET    | `/documents/convert/{job_id}` | 상태 조회                           |
| DELETE | `/documents/convert/{job_id}` | 취소                                |

```json
{ "status": "processing", "stage": "simplifying", "progress": 0.4 }
```

- `stage`: `analyzing` → `simplifying` → `structuring` → `done`
- 로딩 화면 4단계와 짝: `analyzing` = 문서 분석, `simplifying` = 어려운 내용 이해 · 쉬운 글 변환, `structuring` = 중요 정보 정리
- 취소는 다음 조각 처리를 막는 방식이다. 이미 보낸 AI 호출은 중간에 끊지 못한다
- 2026-09-15 프론트 연결 (`src/api/conversion.ts`): 세 요청 모두 요청자를 가린다. 토큰이 있으면 계정, 없으면 기기 번호다 (아래 "9. 기기 번호 · 이용 횟수"). 둘 다 없으면 400 `DEVICE_ID_REQUIRED`. 취소는 상태 응답을 그대로 돌려주고 끝난 작업이면 아무것도 하지 않는다. 결과는 완료 뒤 30분 동안만 남고 지나면 410 `JOB_EXPIRED`, 없으면 404 `JOB_NOT_FOUND`. 작업은 3분을 넘기면 `TIMEOUT` 으로 실패한다
- 작업 소유 확인 (2026-09-17 백엔드 반영): 다른 계정 · 기기가 만든 작업을 조회 · 취소 · 듣기 · 저장하면 404 `JOB_NOT_FOUND` 다. 전에는 작업 ID(UUID)만 알면 남의 결과를 볼 수 있었다
- 프론트는 결과를 받은 뒤에는 상태를 다시 조회하지 않는다. 탭을 오갈 때 다시 받으면 30분이 지난 뒤 보고 있던 결과가 오류 화면으로 바뀌기 때문이다
- 상태 · 결과 응답은 `src/api/documents.ts` 의 `parseDocumentResult` 와 `src/api/conversion.ts` 가 모양을 확인한다. 다르면 `INVALID_RESPONSE` 오류다. 모르는 `kind` 는 `other`, 모르는 `stage` 는 `analyzing` 으로 본다

### 2. 업로드

- 형식: 이미지(JPG · PNG)와 PDF. **HWP 는 받지 않는다** (OCR 엔진이 읽지 못함). 업로드 전에 프론트가 막는다
- 여러 장: `multipart/form-data` 한 요청에 모든 파일을 배열로 보낸다. 서버가 순서대로 이어 붙여 한 문서로 처리한다. 그래서 한 요청에는 **한 문서의 페이지만** 넣어야 한다. 다른 종류의 문서를 섞으면(임대차계약서 + 근로계약서) 서버가 `MIXED_DOCUMENT_TYPE`(422)로 알려 준다 (2026-09-16 백엔드 답변). 업로드(POST)는 202 로 받고, 상태 조회에서 `status: "failed"` + `error.code` 로 온다 (`IMAGE_UNREADABLE` 과 같은 방식). 프론트는 "한 종류의 문서만 넣어주세요" 오류 화면을 보여 준다
- 제한: 이미지 한 장 최대 10MB, 문서 하나 최대 10장. 요청 전체 최대 20MB (2026-09-15 백엔드 확인, `FILE_TOO_LARGE`)
- 형식은 파일 이름의 확장자(jpg · jpeg · png · pdf)로 검사한다. 프론트가 줄인 사진은 `.jpg` 이름으로 올린다 (`src/lib/compress-image.ts`)
- 압축은 프론트가 한다: 긴 변 2000px, JPEG 품질 80% 권장
- 문서 자르기 · 기울기 보정은 서버가 하지 않는다. OCR 엔진이 어느 정도 기울기는 스스로 처리하므로, 카메라 가이드 테두리는 두되 정밀하게 자를 필요는 없다

### 3. 결과 데이터

프론트 초안을 기준으로 백엔드가 만들었다 (문서 종류 분류, 문단 묶기 · 소제목, mustCheck · todos · faqs 추출). 2026-09-15 백엔드 스키마(`DocumentResult`)를 확인해 아래 "결과 데이터" 에 옮겼다.

- 소제목이 없는 문서는 `paragraphs[].title` 이 `null`
- 지원하지 않는 문서 종류는 `mustCheck` · `todos` · `faqs` 가 `null`
- 문서가 아니거나 너무 흐린 사진은 결과 대신 `IMAGE_UNREADABLE` 오류(422). 글자는 읽혔지만 무슨 문서인지 판단하지 못하면 `DOCUMENT_UNRECOGNIZED`(422, 2026-09-16 백엔드 답변). 둘 다 상태 조회의 `failed` 로 온다
- 서버는 원문 · 사진 · 결과를 저장하지 않는다 (2026-09-14 확인). 변환 작업 상태는 캐시(Redis)에 두되 TTL 30분이라 완료 30분 뒤 자동으로 지워진다 (2026-09-17 백엔드 확인). 개인정보처리방침 3항이 이 내용을 그대로 쓴다
- 원문 강조는 **줄 단위(A안)** 다 (2026-09-14 프론트 결정, 2026-09-15 백엔드 반영): 결과에 OCR 줄 목록 `sourceLines: [{ id, text }]` 를 한 번 주고, 문단마다 가리키는 줄 id 만 `sourceLineIds` 로 준다. 줄 안 일부만 강조하는 B안(Figma 원문 보기 모습)은 AI 가 원문을 그대로 옮겨 적어야 해서 깨질 수 있다. 써 보고 부족하면 B안으로 바꾼다. 발췌(강조 줄 + 앞뒤 줄)는 프론트가 만든다 (`src/routes/-result/source-excerpt.ts`)
- `kind` 코드는 `labor_contract` · `lease_contract` · `fine` · `notice` · `other` 다. 백엔드 AI 가 `category`(근로계약서 · 임대차계약서 · 과태료 · 안내문 · 그 외)로 분류하고 코드로 바꾼다
- `paragraphs[].id` 는 순서대로 `p1`, `p2` …, `sourceLines[].id` 는 OCR 순서대로 `e1`, `e2` … 다
- **백엔드에 알릴 것:** `category` 문구가 Figma 이름표(계약서 · 과태료 통지서 · 안내문)와 다르다. 어느 쪽을 쓸지는 `docs/product.md` "확인 필요"

### 4. 오류 형식

```json
{
  "error": {
    "code": "IMAGE_UNREADABLE",
    "message": "사진이 흐려서 글자를 읽을 수 없어요. 다시 찍어주세요."
  }
}
```

- 화면 문구와 버튼(다시 찍기 · 다시 시도 등)은 프론트가 `code` 로 정한다. `message` 는 로그 · 디버깅용으로만 쓰고 화면에 그대로 보여 주지 않는다 (2026-09-15 프론트 결정: 주 사용자가 읽을 문구를 한곳에서 쉬운 말로 검토하고, 영어 · 내부 문구가 새지 않게). 문구는 `src/routes/-result/conversion-error.ts`
- 400 입력 문제(지원하지 않는 형식, 크기 초과 등), 422 읽을 수 없는 사진, 500 서버 오류

### 5. 로그인: JWT (액세스 + 리프레시 토큰)

> **2026-09-17부터 로그인은 꺼져 있다** (`src/lib/features.ts` 의 `LOGIN_ENABLED`, 원티드 의견).
> 지금 쓰는 방식은 아래 "9. 기기 번호 · 이용 횟수" 다. 이 절은 지우지 않는다. 프론트 코드도 지우지 않았고,
> 다시 켤 때 아래 내용(콘솔 설정 · 토큰 정책)을 그대로 쓴다. 백엔드의 로그인 API 도 그대로 살아 있다.

웹과 앱을 함께 지원하려고 쿠키 세션 대신 토큰을 쓴다.

| 메서드 | 경로            | 설명                                                             |
| ------ | --------------- | ---------------------------------------------------------------- |
| POST   | `/auth/kakao`   | 인가 코드 전달 → 토큰 발급                                       |
| POST   | `/auth/google`  | 인가 코드 전달 → 토큰 발급                                       |
| POST   | `/auth/refresh` | 쿠키(앱은 본문)의 리프레시 토큰으로 두 토큰을 새로 발급          |
| GET    | `/users/me`     | 내 정보 `{ id, nickname, provider, email }` (email 은 null 가능) |
| POST   | `/auth/logout`  | 리프레시 토큰 무효 + 쿠키 삭제                                   |
| DELETE | `/users/me`     | 회원 탈퇴 (카카오 연결 끊기 · 구글 토큰 해제)                    |

2026-09-15 백엔드가 실제로 연동했다 (백엔드 `e08f55b` 기준으로 코드와 배포 응답을 확인).

- 로그인 응답(`TokenResponse`)은 `{ accessToken, refreshToken, expiresIn }` 이고, 같은 리프레시 토큰을 쿠키로도 심는다. 웹은 본문의 `refreshToken` 을 읽지 않는다
- `redirectUri` 가 콘솔에 등록한 4개가 아니면 400 `INVALID_REQUEST`. 코드가 틀리면 401 `UNAUTHORIZED`
- 액세스 토큰이 만료되면 401 `TOKEN_EXPIRED`, 모르는 토큰은 401 `UNAUTHORIZED`. 둘 다 갱신해 본다
- 탈퇴 응답은 리프레시 토큰 쿠키를 지우지 않는다 (서버 세션은 지운다). 프론트가 탈퇴 뒤 로그아웃을 한 번 더 부른다
- **백엔드에 알릴 것:** 탈퇴 때 연결 끊기에 로그인할 때 받은 카카오 · 구글 토큰을 쓴다. 이 토큰은 몇 시간이면 만료돼, 로그인하고 오래 지나 탈퇴하면 연결 끊기가 조용히 실패한다. 카카오는 어드민 키로 끊는 방식을 제안한다
- 저장 위치 (2026-09-17 백엔드 반영): 세션 · 이용 횟수는 DB(Supabase), 변환 작업 상태는 캐시(Redis)에 둔다. 재배포해도 로그인이 풀리거나 진행 중이던 변환이 사라지지 않는다. 전에는 모두 서버 메모리였다

- 카카오 · 구글 인가 코드는 프론트가 받는다 (웹은 리다이렉트로 돌아오는 주소). 백엔드는 리다이렉트를 처리하지 않고 코드만 받는다
- 카카오 · 구글 개발자 콘솔(앱 등록, 콜백 주소 등록)은 프론트 담당자가 한다. 코드를 토큰으로 바꾸는 데 필요한 키(구글 클라이언트 시크릿 등)는 백엔드에 따로 안전하게 전달한다
- 비로그인은 변환을 쓸 수 없다 (2026-09-14 프론트 결정). **2026-09-17 뒤집혔다** — 로그인을 끄고 기기 번호 기준 제한을 쓴다 (아래 "9. 기기 번호 · 이용 횟수"). 샘플은 예나 지금이나 로그인 없이 쓴다

#### 콘솔 설정 (2026-09-15 설정, 키 · 아래 내용 백엔드에 전달)

- **콜백 주소:** 두 콘솔에 아래 4개만 등록했다. 로그인 요청의 `redirectUri` 는 이 중 하나여야 하고, 백엔드는 목록에 없는 주소를 받지 않는다. Vercel 미리보기 주소는 PR 마다 바뀌어 등록할 수 없으므로 미리보기에서는 로그인이 안 된다

  | 제공자 | 실서비스                                         | 로컬 개발                                    |
  | ------ | ------------------------------------------------ | -------------------------------------------- |
  | 카카오 | `https://www.ssokssok.site/auth/kakao/callback`  | `http://localhost:5173/auth/kakao/callback`  |
  | 구글   | `https://www.ssokssok.site/auth/google/callback` | `http://localhost:5173/auth/google/callback` |

- **카카오:** 동의항목은 닉네임만 필수 동의로 받는다. 프로필 사진은 화면에서 쓰지 않아 받지 않고, 이메일은 비즈 앱 전환이 필요해 보류했다. REST API 키의 클라이언트 시크릿(카카오 로그인용)이 켜져 있어 토큰 요청에 `client_secret` 이 필요하다. 로그아웃 리다이렉트 URI 는 쓰지 않는다 ("카카오계정과 함께 로그아웃" 을 쓰지 않음)
- **구글:** Google Auth Platform 의 웹 애플리케이션 클라이언트. 게시 상태가 "테스트" 라 테스트 사용자로 넣은 계정만 로그인된다. 출시할 때 "앱 게시" 를 누른다
- **키:** 카카오 REST API 키와 구글 클라이언트 ID 는 공개 값이라 프론트도 쓴다 (`docs/architecture.md` "백엔드 연동"). 두 시크릿은 백엔드에만 있다
- **회원 탈퇴:** 백엔드가 카카오 연결 끊기 · 구글 토큰 해제를 같이 한다

#### 웹 토큰 저장 (2026-09-15 프론트 결정)

- **액세스 토큰(30분):** 로그인 · 갱신 응답 본문으로 받아 프론트 메모리(자바스크립트 변수)에만 둔다. API 요청 헤더 `Authorization: Bearer` 로 보낸다
- **리프레시 토큰(14일):** 백엔드가 HttpOnly 쿠키로 심고, 프론트 코드는 읽지도 보내지도 않는다. 브라우저가 로그인 관련 주소(`Path=/api/auth`) 요청에만 자동으로 붙인다
- 새로고침 · 브라우저를 다시 켜면 메모리가 비므로, 앱을 켤 때 `POST /auth/refresh` 로 액세스 토큰을 다시 받는다. 쿠키가 남아 있는 14일 동안 로그인이 유지된다
- 고른 이유: localStorage 는 끼어든 스크립트(XSS)가 토큰을 가져가 오래 쓸 수 있고, 둘 다 메모리에 두면 새로고침마다 로그인이 풀려 주 사용자(고령층)에게 맞지 않는다. 모바일 앱은 쿠키 대신 본문으로 받아도 된다
- 쿠키 속성 · 갱신 방식은 "백엔드에 보낼 제안" 8번대로 백엔드가 반영했다 (2026-09-15)
- 쿠키는 읽을 수 없어 로그인했는지 알 수 없으므로, 프론트는 "로그인한 적 있음" 표시(참/거짓)만 localStorage 에 두고 표시가 있을 때만 앱을 켤 때 갱신한다 (`docs/architecture.md` "백엔드 연동")

### 6. 샘플 문서

4종을 미리 변환해 두고 그대로 준다. 로그인 없이, 사용량 제한과 무관하게 항상 쓸 수 있다. 샘플 결과의 듣기 · 저장하기도 로그인 없이 쓴다 (2026-09-14 프론트 결정, 경로는 "백엔드에 보낼 제안" 3번).

| 메서드 | 경로                      | 설명                               |
| ------ | ------------------------- | ---------------------------------- |
| GET    | `/documents/samples`      | 샘플 목록                          |

### 9. 기기 번호 · 이용 횟수 (2026-09-17 백엔드 반영)

로그인을 끄면서(위 5번) 요청자를 기기 번호로 가린다.

- 프론트가 브라우저마다 UUID 를 하나 만들어 localStorage 에 두고, 모든 백엔드 요청에 `X-Device-Id` 헤더로 붙인다 (`src/lib/device-id.ts`, `src/api/client.ts`)
- 백엔드는 `Authorization` 헤더가 있으면 계정 기준, 없으면 `X-Device-Id` 기준으로 센다. 두 카운터는 합치지 않아, 로그인 전에 쓴 횟수를 계정에 이어 붙이는 문제가 생기지 않는다
- 둘 다 없으면 400 `DEVICE_ID_REQUIRED`. 프론트가 항상 붙이므로 화면에 나올 일은 없다
- 변환 관련 API 전부에 적용된다: `POST /documents/convert`, 상태 조회 · 취소, 듣기 · 저장, `GET /usage`

| 메서드 | 경로     | 설명                                                          |
| ------ | -------- | ------------------------------------------------------------- |
| GET    | `/usage` | 오늘 남은 횟수 `{ "remaining": 2, "limit": 3 }` (로그인 무관) |

- 하루 3회, 한국 시간 자정에 다시 채운다
- `done` 으로 끝난 변환만 1회를 쓴다. 실패 · 취소 · 분류 오류(`IMAGE_UNREADABLE` · `MIXED_DOCUMENT_TYPE` · `DOCUMENT_UNRECOGNIZED`)는 쓰지 않는다. 2026-09-15 제품 결정대로 정해졌다
- 진행 중인 작업 수도 빼서 계산한다. 탭 · 기기 여러 개로 동시에 올려 한도를 넘길 수 없고, 진행 중인 작업이 있으면 `remaining` 이 그만큼 줄어 보인다 (끝나면 돌아온다)
- 한도를 넘기면 429 `RATE_LIMITED`. 서비스 전체 · 같은 IP 의 오늘 처리량을 넘기면 503 `SERVICE_BUSY` 다. 후자는 내 횟수가 남아 있으므로 "다 썼다" 가 아니라 "지금은 이용자가 많아요" 를 보여 준다
- 프론트는 홈 말풍선에 남은 횟수를 보여 주고(`src/routes/-home/usage-bubble.tsx`), 0 회면 문서 입력을 눌렀을 때 안내 모달만 띄운다. 변환을 요청할 때 저장해 둔 값을 지워 홈에 돌아오면 새로 받는다
- 사용 기록 보관: 하루 지난 기록은 6시간마다 자동으로 지운다 (2026-09-17 백엔드 확인)
- 처리 위치 (2026-09-17 백엔드 확인): OCR · 쉬운 글 변환은 네이버클라우드(국내), DB 는 Supabase(서울), 서버는 Fly.io(일본 도쿄)다. 문서 처리 자체는 국내에서 이뤄지고 서버만 국외다
- 기기 번호는 토큰이 아니다. 가져가도 남의 결과를 볼 수 없고 문서 내용과도 무관하다. 저장소를 쓸 수 없으면(사파리 private 모드) 메모리에만 두고 쓴다
- 지우면(브라우저 저장소 비우기) 횟수가 초기화된다. 막을 수 없는 방식이고, 실질적인 남용 방지는 IP 상한 · 전체 상한이 한다

## 백엔드에 보낼 제안

답변을 보고 생긴 질문을 "열린 질문" 대신 **프론트 제안 + 확인** 으로 적었다. 백엔드는 제안과 다를 때만 알려 주면 된다. 2026-09-14 기준 백엔드 레포에는 스파이크 코드(`/spike/ocr`, `/spike/simplify`)만 있어서, 스파이크에서 확인한 사실도 함께 적었다.

### 알림 (프론트 결정)

- 비로그인은 변환을 쓰지 않는다. 비로그인 사용량 제한은 필요 없다
- 로그인 사용자는 하루 이용 횟수를 둔다 (2026-09-15 회의). 아래 13번
- 원문 강조는 줄 단위(A안)로 시작한다
- 샘플 결과에서는 비로그인도 듣기 · 저장하기를 쓴다 (체험이 목적이라)
- 카카오 · 구글 개발자 콘솔은 프론트 담당자가 설정하고, 필요한 키는 따로 전달한다
- 웹 토큰: 액세스 토큰은 프론트 메모리, 리프레시 토큰은 HttpOnly 쿠키 (위 "웹 토큰 저장", 아래 8번)

### 연결 작업 전에 필요한 것

1. **스키마 먼저** (2026-09-15 반영): 설계안 API 의 요청 · 응답 모델(Pydantic)과 고정 값을 돌려주는 임시 구현이 Swagger 에 올라왔다. 프론트 타입을 맞췄고, 샘플 내용이 채워지면 연결한다
2. **변환 결과 받기** (2026-09-15 반영): 상태 조회가 `status: "done"` 일 때 `result` 를 같이 준다. `status` 는 `queued | processing | done | failed | canceled`, `failed` 면 `error: { code, message }` 를 같이 준다. 프론트는 2초마다 조회하고 1분이 넘으면 4초로 늘린다. 작업 최대 처리 시간(예: 3분)을 넘기면 `failed`(`TIMEOUT`)
3. **결과 임시 보관 · 경로** (2026-09-15 반영, 듣기 · 저장은 아직 빈 응답. 듣기 경로는 2026-09-18 부터 쓰지 않는다): 서버는 결과를 저장하지 않지만 결과 화면에서 듣기 · 저장을 쓰려면 잠시 들고 있어야 한다. 완료 뒤 30분 동안만 들고 있고, 듣기 · 저장은 `job_id` 로 부른다: `/documents/convert/{job_id}/paragraphs/{i}/audio`, `/documents/convert/{job_id}/export`. 30분이 지나면 `JOB_EXPIRED`. 샘플은 `/documents/samples/{id}/paragraphs/{i}/audio` · `/documents/samples/{id}/export` 를 토큰 없이
4. **표기 · 경로** (2026-09-15 반영): 응답 JSON 은 camelCase 로 맞춘다. Pydantic `alias_generator=to_camel` 설정 한 줄이면 되고 TypeScript 관례와 같아 변환 코드가 필요 없다 (스파이크는 snake_case). 모든 API 는 `/api` 아래에 둔다 (스파이크는 접두사 없음). 배포 때 같은 도메인이면 `/api` 만 서버로 넘기면 되고 개발 프록시도 그대로 쓴다

### 화면 작업 때 필요한 것

5. **오류 code 목록**: 아래 표를 기준으로 더하거나 고칠 것만 알려 준다. 화면 문구는 프론트가 code 별로 정하므로, 새 code 를 만들면 꼭 알려 준다 (모르는 code 는 "잠시 뒤에 다시 시도해주세요" 로 보인다)

   | code                    | HTTP | 프론트 동작                                      |
   | ----------------------- | ---- | ------------------------------------------------ |
   | `INVALID_REQUEST`       | 400  | 요청 형식 오류 (로그인이면 실패 화면)            |
   | `UNSUPPORTED_FORMAT`    | 400  | 다른 파일 고르기                                 |
   | `FILE_TOO_LARGE`        | 400  | 다른 파일 고르기                                 |

   | `IMAGE_UNREADABLE`      | 422  | 다시 찍기                                        |

6. **업로드 크기** (2026-09-15 일부 반영: 요청 전체 20MB. PDF 페이지 수 제한은 없다): 프론트가 줄인 사진은 장당 1MB 안팎이라 10장이어도 10MB 쯤이다. 요청 전체 최대 20MB, PDF 는 파일 20MB · 10페이지를 제안한다. 요청 중에는 프론트가 버튼을 잠가 같은 변환을 두 번 보내지 않는다
7. **원문 모양 (A안)** (2026-09-15 반영, 위 "3. 결과 데이터"): 스파이크처럼 OCR 줄 목록을 결과에 한 번 주고 (`sourceLines: [{ id, text }]`), 문단마다 줄 번호만 준다 (`sourceLineIds: ["e3", "e4"]`). 프론트가 그 줄을 강조하고 앞뒤 줄을 함께 보여 준다. 문단마다 원문을 되풀이하지 않아 응답이 작고, 스파이크 방식 그대로라 만들기 쉽다. 샘플의 "원문 텍스트" 도 같은 필드로 준다
8. **로그인 토큰** (2026-09-15 백엔드 반영, 위 "5. 로그인"): `POST /auth/refresh` 로 액세스 토큰을 새로 받는다. 액세스 30분 · 리프레시 14일, 로그인 요청 본문은 `{ code, redirectUri }`. 토큰 없는 변환 요청은 401(`UNAUTHORIZED`). 하루 이용 횟수는 아래 13번
   - 웹의 로그인 · 갱신 응답: 액세스 토큰은 본문, 리프레시 토큰은 쿠키 `HttpOnly; Secure; SameSite=Strict; Path=/api/auth; Max-Age=1209600`. `Max-Age` 가 없으면 브라우저를 닫을 때 지워진다
   - `/auth/refresh` 는 본문이 아니라 쿠키에서 리프레시 토큰을 읽는다. `/auth/logout` 은 쿠키를 지운다 (`Max-Age=0`)
   - 갱신할 때마다 새 리프레시 토큰으로 바꾼다(교체). 자주 쓰면 14일이 계속 늘어난다. 발급한 리프레시 토큰은 서버에 기록해 로그아웃 · 탈퇴 때 무효로 만든다
   - 교체 직후 몇 초(예: 10초)는 바로 전 토큰도 받는다. 탭 여러 개가 동시에 갱신하면 옛 토큰이 한 번 더 올 수 있어서, 도난으로 오해해 로그아웃시키지 않게 한다
9. **내 정보** (2026-09-15 백엔드 반영): `/users/me` 가 `{ id, nickname, provider, email }` 을 준다. 설정 화면은 이메일 대신 닉네임을 보여 준다. 카카오는 이메일 동의항목을 보류해서(위 "콘솔 설정") `email` 이 `null` 이다
10. **듣기 · 저장 세부**: 듣기는 기기 음성으로 바꿔 음성 API 가 필요 없다 (2026-09-18, 위 "7. 듣기 · 저장하기"). PDF 는 `application/pdf` 에 `Content-Disposition: attachment` (파일 이름 포함)
11. **샘플 id** (2026-09-15 반영): 프론트 목데이터와 같은 `work-contract` · `house-contract` · `pension-notice` · `fine` 을 쓰면 연결할 때 바꿀 곳이 없다
12. **샘플 내용** (2026-09-15 백엔드 답변: 실제 문서 4종을 변환해 DB 에 저장): 채워지면 알려 주면 프론트가 배포 서버에서 화면을 확인한다. 이름표(`category`) 문구는 `docs/product.md` "확인 필요"
13. **하루 이용 횟수** (2026-09-17 백엔드 반영 · 배포 확인): 정해진 내용은 위 "9. 기기 번호 · 이용 횟수" 로 옮겼다. 처음에는 로그인 계정당 하루 3회였고, 요청할 때 횟수를 써서 실패 · 취소도 1회를 쓰는 점과 남은 횟수 조회 API 가 없는 점을 프론트가 다시 요청했다. 백엔드가 세 가지를 모두 반영했다: `done` 일 때만 소모, `GET /usage` 신설, 형식 · 크기 검사를 횟수 확인보다 먼저

### 아직 답을 못 받은 것 (2026-09-17)

- **AI · OCR 제공자 예산 하드 상한 + 알림.** 코드가 뚫려도 손실을 멈추는 유일한 장치라 가장 먼저 요청했는데 답이 없다
- **IP 상한 값.** `SERVICE_BUSY` 는 만들었지만 몇 회인지, 공유망(복지관 · 기숙사 · 통신사 NAT)을 고려했는지 모른다. IP 단독 차단은 주 사용자가 막히므로 하지 않기로 했다
- **기기 · IP 별 사용량 로그.** 한도값을 정하려면 실제 사용 데이터가 필요하다
- 프로덕션 Swagger 는 답이 없었지만 2026-09-17 확인 결과 `https://ssokssok-backend.fly.dev/docs` 가 404 라 닫혔다
- 처리 위치 · 보관 기간은 2026-09-17 답을 받아 개인정보처리방침(`src/routes/privacy.tsx`)에 반영했다
- 배포 직후 `GET /api/usage` 가 한 번 500 을 냈다. 뒤이어 12번은 모두 정상이라 롤아웃 중 문제로 보이지만, 재발하면 백엔드에 알린다
